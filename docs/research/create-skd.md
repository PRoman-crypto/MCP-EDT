# create_skd — генерація схем компоновки даних (Template.dcs)

Дата: 2026-08-28. Статус: клас `tools/write/SkdBuilder.java` написано, весь проєкт
компілюється (`javac --release 17`, classpath — блок `$cp` із `build.ps1`). У
`ToolRegistry` окремого інструмента **не** додавалось: `SkdBuilder.buildDcs`
викликається з уже наявного `TemplateOps.createTemplate` при
`templateFormat: "dcs"`. `setDataSetQuery` поки не має виклику з жодного
інструмента — це окремий крок (див. «Що лишилось»).

## Підхід

Той самий, що в `MxlBuilder`: рядковий серіалізатор XML на gson + `StringBuilder`,
без EMF і без `com._1c.g5.v8.dt.dcs.model.*`. Формат `.dcs` простий і стабільний,
а «зворотний бік» — наш `GetSkdTool` — теж читає його DOM-ом із літеральними
префіксами (`dcsset:`, `v8:`), тож генератор і парсер узгоджені за конструкцією.

Точкова правка (`setDataSetQuery`) зроблена **рядковим** пошуком блоків, а не DOM:
`Transformer` переформатував би весь файл (пробіли, порядок атрибутів, декларації
просторів імен), а нам важливо, щоб діф у git містив лише текст запиту. Перевірено:
після заміни збігаються 1792 символи префікса і 11571 символ суфікса — рівно тіло
`<query>` і змінилось.

## Специфікація spec

Усі поля необов'язкові; порожня специфікація (`{}` — саме її передає
`createTemplate` без `spec`) дає валідну порожню схему.

```json
{
  "lang": "ru",
  "dataSourceName": "ИсточникДанных1",

  "dataSets": [
    {
      "name": "НаборДанных1",
      "type": "Query",
      "query": "ВЫБРАТЬ …",
      "objectName": "ТаблицаЗначений",
      "autoFillFields": true,
      "fields": [
        "Номенклатура",
        {"name": "Количество", "title": "Кількість", "type": "Число(15,3)", "field": "Кол"}
      ],
      "items": [ { …вкладений набір… } ]
    }
  ],

  "dataSetLinks": [
    {"source": "Продажи", "destination": "Остатки",
     "sourceExpression": "Номенклатура", "destinationExpression": "Номенклатура",
     "parameter": "Отбор"}
  ],

  "calculatedFields": [
    {"name": "СредняяЦена", "expression": "Сумма / Количество",
     "title": "Середня ціна", "type": "Число(15,2)"}
  ],

  "resources": [
    {"field": "Количество"},
    {"field": "Сумма", "expression": "Сумма(Сумма)", "groups": ["Номенклатура"]}
  ],

  "parameters": [
    {"name": "Период", "type": "СтандартныйПериод", "title": "Період"},
    {"name": "Дата1", "type": "Дата", "expression": "&Период.ДатаНачала", "restricted": true},
    {"name": "Склад", "type": "СправочникСсылка.Склады"},
    {"name": "Комментарий", "type": "Строка(100)", "availableAsField": false, "use": "Always"}
  ],

  "variants": [
    {"name": "Основной", "title": "Основний",
     "selection": ["Номенклатура", "Количество"],
     "groupings": ["Номенклатура"]}
  ]
}
```

Пояснення до полів:

| Поле | Типово | Зміст |
|---|---|---|
| `lang` | `ru` | мова всіх `LocalStringType` (заголовки полів, параметрів, подання варіантів) |
| `dataSourceName` | `ИсточникДанных1` | ім'я єдиного локального джерела даних |
| `dataSets[].type` | висновок | `Query` \| `Object` \| `Union` (аліаси: `Запрос`/`Объект`/`Объединение`, `DataSetQuery`…). Без `type`: є `items` → Union, є `objectName` → Object, інакше Query |
| `dataSets[].fields` | з запиту | рядок = скорочення для `{"name": …}`; об'єкт: `name` (він же `dataPath`), `title`, `type`, `field` (вихідне поле, якщо відрізняється від `name`) |
| `dataSets[].autoFillFields` | не пишеться (=true) | `false` → `<autoFillFields>false</autoFillFields>`; за замовчуванням автозаповнення лишається ввімкненим, і EDT сам виправить список полів при відкритті |
| `resources[]` | — | рядок або об'єкт; `expression` типово `Сумма(<field>)`; `groups` — перелік групувань, для яких рахувати ресурс |
| `parameters[].restricted` | `false` | `<useRestriction>` — «обмеження використання» |
| `parameters[].use` | не пишеться | `Auto` \| `Always` |
| `variants[].selection` | авто | без нього — `SelectedItemAuto` (усі доступні поля) |
| `variants[].groupings` | детальні записи | без нього — `StructureItemGroup` без `groupItems` (143 таких групи в реальних схемах retail) |
| `variants` | один «Основной» | якщо є хоч один набір даних, а `variants` не задано, генерується варіант `Основной` з авто-вибіркою; для порожньої схеми варіант не пишеться |

Скорочення верхнього рівня: якщо `dataSets` немає, але є `query` (і, за потреби,
`fields`/`objectName`), будується один набір `НаборДанных1`. Тобто мінімальний
робочий виклик — це просто `{"query": "ВЫБРАТЬ …"}`.

### Типи значень (`type` у полях, обчислюваних полях і параметрах)

`Строка[(N)]`, `Число[(N,M)]`, `Дата`/`ДатаВремя`, `Булево`,
`СтандартныйПериод`, `УникальныйИдентификатор`, `СписокЗначений`, а також
посилальні: `СправочникСсылка.X`, `ДокументСсылка.X`, `ПеречислениеСсылка.X`,
`ПланВидовХарактеристикСсылка.X`, `ПланСчетовСсылка.X`,
`ПланВидовРасчетаСсылка.X`, `ПланОбменаСсылка.X`, `БизнесПроцессСсылка.X`,
`ЗадачаСсылка.X` (і їхні англійські відповідники `CatalogRef.X` тощо).

Кілька типів — через кому: `"СправочникСсылка.Склады,СправочникСсылка.Магазины"`
(кома всередині дужок, як у `Число(15,2)`, роздільником не вважається). Для
складеного типу кваліфікатори не пишуться, а значення параметра — `xsi:nil`.
Невідомий тип → помилка з переліком підтриманих.

## Обов'язкові елементи .dcs і чому саме вони

Звірено з еталонами `int_ДлинаЧека` (простий Query-набір) і
`СведенияОПользователях` (3 набори + `dataSetLink` + 3 варіанти).

1. **Корінь** `<DataCompositionSchema>` з повним набором 8 просторів імен
   (`default`, `dcscom`, `dcscor`, `dcsset`, `v8`, `v8ui`, `xs`, `xsi`).
   Харнес звіряє їх з еталоном — збігаються символ у символ. `dcscom`/`v8ui` нам
   не потрібні, але EDT пише їх завжди, а зайва декларація нічого не коштує.
2. **`<dataSource>`** з `<name>` і `<dataSourceType>Local</dataSourceType>` —
   кожен набір посилається на нього елементом `<dataSource>`; без джерела набір
   «висить у повітрі». Пишемо тільки якщо є хоч один набір.
3. **`<dataSet xsi:type="DataSetQuery|DataSetObject|DataSetUnion">`**: `xsi:type`
   обов'язковий (без нього тип абстрактний), далі — `name`, `field*`,
   `dataSource`, потім `query` (Query) або `objectName` (Object), або `item*`
   (Union; у Union власного `dataSource` немає). Порядок дочірніх елементів — це
   `sequence` XML-схеми, тому він фіксований, а не косметичний.
4. **`<field xsi:type="DataSetFieldField">`** з `dataPath` + `field`. `title` і
   `valueType` опційні: у `int_ДлинаЧека` половина полів запитного набору взагалі
   без типу — тип підтягується із запиту.
5. **Порядок топ-рівневих елементів**: `dataSource`, `dataSet`, `dataSetLink`,
   `calculatedField`, `totalField`, `parameter`, `settingsVariant`. Перевірено на
   трьох реальних схемах (`int_ДлинаЧека`, `СведенияОПользователях`,
   `ОбъемНенужныхФайлов`) — усі три збігаються.
6. **Порядок дочірніх у `<parameter>`**: `name`, `title`, `valueType`, `value`,
   `useRestriction`, `expression`, `availableAsField`, `use`. Саме такий порядок
   (`expression` **перед** `availableAsField`) пише EDT — знайдено параметри, де
   присутні обидва.
7. **`<settingsVariant>`**: `dcsset:name`, `dcsset:presentation`,
   `dcsset:settings`. Усередині `settings` порядок теж за схемою:
   `selection`, `filter`, `dataParameters`, `order`, `conditionalAppearance`,
   `outputParameters`, `item*`. Ми пишемо мінімум — `selection`, за потреби
   `outputParameters` (лише «Заголовок») і один `item` типу
   `dcsset:StructureItemGroup` (групування або детальні записи).
8. **`userSettingID` не пишемо** — це GUID-и користувацьких налаштувань, у схемі
   вони необов'язкові; EDT згенерує їх при першому редагуванні варіанта.

## Автогенерація полів із тексту запиту

Якщо у наборі типу Query не задано `fields`, список колонок витягується з тексту
запиту. Алгоритм (`SkdBuilder.parseQueryFields`):

1. **Санітизація зі збереженням зміщень**: вирізаються коментарі `//…`, вміст
   рядкових літералів (`"…"`, з урахуванням подвоєних лапок) і блоки-розширення
   СКД `{ВЫБРАТЬ …}` / `{ГДЕ …}` (з балансуванням фігурних дужок).
2. **Пакетний запит**: береться останній запит пакета (роздільник `;` поза
   дужками) — саме він визначає поля СКД.
3. **`ВЫБРАТЬ`/`SELECT`** шукається поза круглими дужками (щоб не зачепити
   підзапит), далі пропускаються `РАЗРЕШЕННЫЕ`/`ALLOWED`,
   `РАЗЛИЧНЫЕ`/`DISTINCT`, `ПЕРВЫЕ N`/`TOP N`.
4. **Кінець секції вибірки** — перше ключове слово верхнього рівня з переліку:
   `ИЗ`, `ГДЕ`, `СГРУППИРОВАТЬ`, `ИМЕЮЩИЕ`, `УПОРЯДОЧИТЬ`, `ИТОГИ`,
   `ОБЪЕДИНИТЬ`, `ПОМЕСТИТЬ`, `ИНДЕКСИРОВАТЬ`, `АВТОУПОРЯДОЧИВАНИЕ` (+ англійські
   `FROM`, `WHERE`, `GROUP`, `HAVING`, `ORDER`, `TOTALS`, `UNION`, `INTO`,
   `INDEX`, `AUTOORDER`).
5. **Розбиття по комах верхнього рівня** (кома всередині дужок — не роздільник).
6. **Ім'я колонки**: останній `КАК`/`AS` на нульовому рівні дужок → псевдонім
   (тому `ВЫРАЗИТЬ(… КАК ЧИСЛО(12,2)) КАК ДлинаЧека` дає `ДлинаЧека`, а не
   `ЧИСЛО`). Якщо `КАК` немає — вираз має бути простим шляхом
   (`Товары.Номенклатура` → `Номенклатура`).

### Межі автопарсера

- **Вираз без псевдоніма не розбирається**: `ВЫБРАТЬ СУММА(Т.Сумма) ИЗ …` →
  помилка «Не вдалося визначити ім'я колонки для «СУММА(Т.Сумма)» … Додайте
  псевдонім (… КАК ІмʼяПоля) або задайте список fields явно». Це свідомо: 1С теж
  вимагає псевдонім для такої колонки.
- **`ВЫБРАТЬ *` і `Таблица.*` не підтримуються** — потрібен явний `fields`.
- **Повтор імені колонки** (напр. дві колонки з однаковим псевдонімом у різних
  гілках) → помилка з проханням задати `fields`.
- Береться **лише останній запит пакета**; поля з тимчасових таблиць у середині
  пакета ігноруються (це правильно для СКД, але якщо пакет закінчується
  `ПОМЕСТИТЬ`, полів не буде — помилка).
- Для **`ОБЪЕДИНИТЬ ВСЕ`** беруться колонки лише **першого** `ВЫБРАТЬ` (як і в
  самій мові запитів — імена колонок задає перший запит об'єднання).
- **Типи полів не визначаються** — виводяться лише імена; тип підтягне 1С/EDT при
  автозаповненні (`autoFillFields` за замовчуванням лишається ввімкненим).
- **Заголовки полів не генеруються** — тільки якщо задані у `fields`.
- Парсер не є повноцінним парсером мови запитів: він не перевіряє синтаксис і не
  «розуміє» `ВЫБОР…КОНЕЦ` глибше, ніж треба для підрахунку дужок і пошуку `КАК`.

## setDataSetQuery — точкова заміна тексту запиту

```java
String patched = SkdBuilder.setDataSetQuery(existingDcsXml, "НаборДанных1", newQuery);
```

- Знаходить блок `<dataSet …>` (або вкладений `<item …>` усередині
  `DataSetUnion`), чиїм першим дочірнім `<name>` є вказане ім'я, з підрахунком
  вкладеності однойменних тегів.
- Замінює вміст `<query>…</query>` (підтримано й порожній `<query/>`; якщо
  елемента немає — вставляє перед `<autoFillFields>`, тобто в правильне місце
  послідовності XML-схеми).
- Решта файлу лишається символ у символ; екрануються лише `&`, `<`, `>`
  (лапки в тексті запиту не чіпаємо — EDT їх теж не екранує).
- Помилки: набір не знайдено (з переліком доступних імен), набір не типу Query
  (`DataSetObject`/`DataSetUnion` тексту запиту не мають), пошкоджений XML,
  задовгий запит (ліміт 100 000 символів).

## Самоперевірка (офлайн-харнес, scratchpad)

Харнес `SkdHarness.java` компілювався разом з усім проєктом (той самий classpath),
кожна згенерована схема проганялась через `DocumentBuilder.parse` і через **копію
логіки `GetSkdTool`** (ті самі методи розбору DOM).

| Схема | Згенеровано | Що прочитав парсер `get_skd` |
|---|---|---|
| 1. Query + явні `fields` | 2412 симв.; топ-рівень `dataSource, dataSet, settingsVariant` | 1 набір `DataSetQuery` «НаборДанных1», повний текст запиту, 2 поля (`Номенклатура`; `Количество` з заголовком «Кількість» і типом `decimal`), варіант «Основной» |
| 2. Той самий запит **без** `fields` (автопарсер) | 2261 симв. | 4 поля: `Номенклатура` (крапковий шлях), `Склад`, `Средняя` (з `ВЫРАЗИТЬ(… КАК ЧИСЛО(12,2)) КАК …`), `Признак` (з `ВЫБОР…КОНЕЦ КАК …`). Модифікатори `РАЗРЕШЕННЫЕ РАЗЛИЧНЫЕ ПЕРВЫЕ 100`, блок `{ВЫБРАТЬ …}`, коментар `// … ИЗ і ГДЕ` і рядкові літерали `"Так"/"Ні"` не завадили |
| 3. Повна: 2 набори (Query + Object), зв'язок, обчислюване поле, 2 ресурси, 5 параметрів, 2 варіанти | 8211 симв.; топ-рівень `dataSource, dataSet×2, dataSetLink, calculatedField, totalField×2, parameter×5, settingsVariant×2` | усе прочитано: `dataSetLinks`, `calculatedFields`, `resources` (у т.ч. `Сумма(Количество)` за замовчуванням і `groups:["Номенклатура"]`), параметри з типами `StandardPeriod`/`dateTime`+`expression`+`restricted`/`CatalogRef.Склады`/`string`/`boolean`, варіанти з `selection` і `groupings` |
| 4. Порожня (`{}`) | 525 симв., лише корінь із просторами імен | `{"dataSets":[]}` — well-formed, без наборів і варіантів |

Негативні сценарії (усі дали зрозумілі повідомлення українською):
набір `Object` без `objectName`; вираз без псевдоніма; невідомий тип параметра
(`Магия`); ресурс на неоголошене поле; `ВЫБРАТЬ *`.

Звірка з еталоном `int_ДлинаЧека`: набір просторів імен кореня збігається
повністю (`namespaces збігаються: true`); порядок топ-рівневих елементів той
самий; ідіоми `StructureItemGroup` без `groupItems` (143 випадки в retail) і
`selection` з `SelectedItemAuto` (8 схем) у реальних файлах присутні.

`setDataSetQuery` перевірено на **копії** `int_ДлинаЧека/Template.dcs` у
scratchpad (оригінал звірено після тесту — не змінився):
файл лишився well-formed, топ-рівнева структура ідентична (16 параметрів, 4
ресурси, 1 варіант), новий текст запиту читається назад символ у символ,
незмінними лишились 1792 симв. префікса і 11571 симв. суфікса. Негативний
сценарій (`НемаТакого`) повернув перелік доступних наборів.

## Обмеження генератора (свідомо, поки не запитають)

- Одне локальне джерело даних (`dataSourceType=Local`); зовнішні джерела і
  вкладені схеми (`nestedDataSet`) не підтримуються.
- Немає внутрішніх макетів оформлення СКД (`<template>`), умовного оформлення
  (`conditionalAppearance`), `appearance` полів, ролей полів (вимір/період/
  рахунок), `useRestriction` на полях, папок полів (`DataSetFieldFolder`).
- У варіантах немає відборів (`filter`), порядку (`order` — тільки авто),
  значень параметрів даних (`dataParameters`), кількох рівнів структури
  (генерується рівно один `StructureItemGroup`), таблиць і діаграм
  (`StructureItemTable`/`StructureItemChart`), `outputParameters` крім
  «Заголовок».
- Ресурси не перевіряються на «поле — не групування»; перевірка лише на те, що
  поле оголошене (і лише коли в усіх наборах поля відомі).
- Ліміти: 50 наборів, 500 полів на набір, 200 параметрів, 20 варіантів,
  100 000 символів на запит.

## Приклади викликів

Через уже наявний `createTemplate` (`TemplateOps`), `templateFormat: "dcs"`:

```json
{"kind": "Report", "name": "МійЗвіт", "template": "ОсновнаяСхемаКомпоновкиДанных",
 "templateFormat": "dcs", "dryRun": true,
```

## Що лишилось (не робилось — заборона правити існуючі файли)

1. `setDataSetQuery` нікуди не під'єднано. Природне місце — операція
   `setTemplateContent` у `TemplateOps` (зараз вона жорстко працює з
   `Template.mxlx` і `MxlBuilder`) або окрема операція `editSkd` в
   `EditMetadataTool` з параметрами `kind/name/template/dataSet/query`.
2. Живий тест після деплою: `createTemplate` з `templateFormat:"dcs"` і
   `dryRun:true` (перегляд XML), потім без `dryRun` у тестовому звіті, далі
   `get_skd` на створеному макеті і `get_validation_errors` на об'єкті.
3. Ідея на майбутнє: діставати типи полів із `validate_query`, щоб автопарсер
   заповнював `valueType` і заголовки.
