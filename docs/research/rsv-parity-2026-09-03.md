## P1 — дефекти: інструмент повертає неправильну відповідь

### 1. `validate_query` — «валідний» для запиту з неіснуючим полем (false OK)

```
project=cfe  ВЫБРАТЬ Тбл.НетТакогоПоля КАК Поле ИЗ Справочник.ВидыНоменклатуры КАК Тбл
наш:       {"valid": true, "level": "syntax", "note": "Семантична перевірка недоступна
           (NullPointerException: ...IResourceSetProvider.get(...) because the return value of
           IResourceServiceProvider.get(java.lang.Class) is null) — виконано лише синтаксичну."}
оригінал:  {"issues":[{"severity":"ERROR","message":"Поле 'Тбл.НетТакогоПоля' не найдено",
           "line":1,"column":13,"offset":12,"length":13,"code":"Field not found"}]}
```

Семантичний прохід падає з NPE і ми **мовчки деградуємо до синтаксичного**, віддаючи
`valid:true`. Для агента це найгірший сценарій: він вставить у модуль неробочий запит.
NPE відтворюється на будь-якому синтаксично коректному запиті, де таблиця резолвиться.

### 2. `validate_query` — «таблиця не знайдена» для існуючої таблиці (false ERROR)

```
project=cf   ВЫБРАТЬ Тбл.Ссылка КАК Ссылка ИЗ Справочник.ВидыНоменклатуры КАК Тбл
наш:       {"valid":false,"level":"semantic","errors":[
             {"message":"Таблица с именем 'Справочник.ВидыНоменклатуры' не найдена"},
             {"message":"Поле 'Тбл.Ссылка' не найдено"}]}
оригінал:  {"issues":[],"message":"Запрос синтаксически корректен"}
```

Довідник у `cf` існує. Схоже, scope не прив'язується до вказаного проєкту (на `cfe`
той самий запит проходить інакше). Разом із п.1 виходить, що семантична перевірка
запитів у нас недостовірна в обидві сторони.

### 3. `validate_query` — немає прапорця `isDcs`

Запит СКД проганяється звичайним QL-парсером:

```
ВЫБРАТЬ {ВЫБРАТЬ Тбл.Ссылка} ИЗ Справочник.ВидыНоменклатуры КАК Тбл
наш:       4 помилки, серед них сміттєві «Поле 'ВЫБРАТЬ' не найдено»,
           «Нельзя использовать '.' и пробельные символы в псевдонимах»
оригінал (isDcs=true): 3 по суті, зокрема
           «Имя выбираемого поля компоновки данных должно быть в выбираемых полях»
```

## P2 — відповідь бідніша за оригінал

### 6. `get_object_details` для об'єкта розширення: немає `baseObject`

Для `Catalog.ВидыНоменклатуры` у `cfe` ми віддаємо 2 власні реквізити розширення (889 симв.).
Оригінал додає блок `baseObject` — синонім, uuid і **повний список реквізитів базового
об'єкта з типами** (`CatalogRef.X`, `EnumRef.X`), включно з `choiceParameters` та
`choiceParameterLinks` (21 124 симв.). Для роботи з розширенням це ключовий контекст.

На основній конфігурації (`cf`) наша відповідь навпаки повніша (36 136 проти 23 389):
типи реквізитів у нас є, українською/російською іменовані (`Булево`,
`ПеречислениеСсылка.ВариантыОказанияУслуг`), є `standardAttributes`, `inputByString`,
`templates` із синонімами.

### 7. `get_object_details` для звіту: немає зведення СКД

Оригінал додає `dcsTemplates` (набори даних, кількість полів, довжина запиту, параметри
з виразами) і `modules{objectModule,managerModule,recordSetModule}`. У нас на це є
окремий `get_skd` — вирішити, чи потрібне зведення прямо в деталях об'єкта.

### 8. `get_object_help` — немає довідки форм

`Document.ЧекККМ` у `cf`: ми віддаємо лише `src/Documents/ЧекККМ/Help/ru.html`.
Оригінал збирає ще `Forms/ФормаДокумента/Help/ru.html` і `Forms/ФормаДокументаРМК/Help/ru.html`,
плюс `synonym`, `comment`, `mdoPath` (7 280 проти 15 940 симв.).

### 9. `ai_context` — немає цілі «форма», для модуля не вкладає структуру

Оригінал приймає `target=Catalog.X.Form.Y` і повертає повне дерево форми (87 005 симв.).
У нас `kind`+`name` описують лише об'єкт; для форми відповіді немає взагалі.
Для `CommonModule` ми віддаємо зведення (`path`, `totalLines`, `methodCount`,
`exportMethods`) і хінт «тіла методів — read_method_source», оригінал одразу вкладає
`moduleStructure`. Задум `ai_context` — зібрати все за один виклик, тож хінт суперечить меті.

### 10. `code_search` — немає операції `resolveSymbol`

`ISB_ПостроительФормы.ОписаниеТипаЧисло` у нас іде як текстовий пошук → `0 matches`.
Оригінал резолвить символ і повертає модуль, тип, сигнатуру, рядки, тіло, doc-коментар.
Нашим `find_references` це не закривається — він вимагає path+method, тобто відповідь
на «де це визначено?» треба знати наперед.

### 11. `get_module_structure` / `read_method_source` — немає `parameters`, `doc`, `region`

Рядки, сигнатура, export у нас є. Немає: розібраних параметрів зі значеннями за
замовчуванням, розібраного doc-коментаря (опис + типи параметрів) і прив'язки методу до
області. Регіони ми повертаємо окремим списком, але метод із областю не пов'язаний.
Дрібниця: у нашій сигнатурі немає пробілу після коми (`(А = 15,Б = 2)`).

### 12. `list_metadata_objects` / `list_modules` — бідніші поля і фільтри

`list_metadata_objects`: у нас `name` (+`synonym`), в оригіналі ще `fullName`, `uuid`,
`attributesCount`, `formsCount`, `commandsCount`, `hierarchical`.
`list_modules`: у нас `path`/`moduleType`/`owner`, в оригіналі ще `sizeBytes`, `linesCount`,
`ownerObjectType`, а також фільтри `moduleType`/`objectName`/`objectType`, `sortBy`, `compact`.

### 13. `diff_module` — базлайн лише сесійний, git не читається

```
наш:       {"hasBaseline": false, "message": "Модуль не змінювався через write_module_source
           у поточній сесії EDT — базлайну для diff немає."}
оригінал:  порівняння з git (режими summary/unified/methods)
```

Наш `diff_module` показує тільки те, що сам записав. Оригінал позиціонується як diff із
VCS. Побічно: на цьому файлі оригінал теж помилився — віддав `isNewFile:true`, хоча файл
у git є (`28d02231f`), тобто його git-детект теж не бездоганний.

## P3 — формат відповіді

### 14. `validate_query` — у помилках немає `severity`, `offset`, `length`, `code`

У нас лише `line`/`column`/`message`. Оригінал дає ще зміщення й довжину фрагмента
та стабільний код діагностики (`Field not found`, `Table not found`, `syntax`) —
за ним агент може приймати рішення програмно. Немає й лічильників (`errors`/`warnings`).

### 15. `get_form_image` (structure) — немає лічильників і пагінації

Дерево елементів у нас повне й порівнянне за обсягом (61 977 проти 74 392 симв.), але
немає `totalElements`/`returnedElements` і параметрів `subtree`, `maxElements`, `depth`,
які в оригіналі дозволяють читати великі форми частинами.
